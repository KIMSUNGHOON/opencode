# Dual Model Strategy Report: Qwen3-Coder-Next-FP8 Endpoint 추가 전략

## 1. Executive Summary

현재 Code QA v4 워크플로우는 **Qwen3-Next-Thinking-80B-A3B-FP8** 단일 모델로 오케스트레이터 + 11개 서브 에이전트를 운영하고 있다. 본 리포트는 **Qwen3-Coder-Next-FP8** 모델 엔드포인트를 추가하여 듀얼 모델 전략을 수립하기 위한 분석과 제안을 담고 있다.

---

## 2. 현재 시스템 분석

### 2.1 현재 모델: Qwen3-Next-Thinking-80B-A3B-FP8

| 항목 | 값 |
|------|-----|
| 총 파라미터 | 80B (활성: 3B, Sparse MoE) |
| Context Window | 256K tokens |
| Output Limit | 16K tokens |
| 양자화 | FP8 (~76GB VRAM) |
| 모드 | Thinking (CoT) + Tool Calling |
| 배포 | 2x H100 NVL 96GB (TP=2) |

### 2.2 신규 모델: Qwen3-Coder-Next-FP8

| 항목 | 값 |
|------|-----|
| 총 파라미터 | 80B (활성: 3B, Sparse MoE) |
| Context Window | 256K tokens (최대 1M 확장 가능) |
| 양자화 | FP8 (단일 GPU에서 256K 서빙 가능) |
| 모드 | **Non-thinking** (`<think>` 블록 없음) |
| 코딩 특화 | SWE-Bench Verified 70.6% |
| 언어 지원 | 370개 프로그래밍 언어 |
| 학습 기반 | Qwen3-Next-80B-A3B-Base + 600B 토큰 repo-level 데이터 |
| 추론 속도 | ~43 tok/s (DGX Spark, FP8) |
| 라이선스 | Apache 2.0 |
| SGLang 요구 | >= v0.5.8 |
| vLLM 요구 | >= 0.15.0 |

### 2.3 두 모델의 핵심 차이점

```
┌─────────────────────────────────────────────────────────────────────────────────────┐
│                          모델 비교 매트릭스                                            │
├──────────────────────┬──────────────────────────┬──────────────────────────────────┤
│ 특성                 │ Thinking (현재)           │ Coder-Next (신규)                │
├──────────────────────┼──────────────────────────┼──────────────────────────────────┤
│ 추론 모드            │ Thinking (CoT 내부 포함)   │ Non-thinking (직접 응답)          │
│ 강점                 │ 복잡한 추론, 분석, 계획     │ 코드 생성/수정, SWE 태스크        │
│ 응답 속도            │ 느림 (thinking overhead)   │ 빠름 (non-thinking)              │
│ 토큰 효율            │ 낮음 (think 토큰 소비)     │ 높음 (모든 토큰이 유효 출력)       │
│ Tool Calling         │ 지원                      │ 지원                             │
│ 코드 품질            │ 좋음                      │ 매우 좋음 (SWE-Bench 70.6%)       │
│ 보안 코드 생성       │ 좋음                      │ 매우 좋음 (Claude Opus 4.5 상회)   │
│ 아키텍처 기반        │ Qwen3-Next-80B-A3B-Base   │ Qwen3-Next-80B-A3B-Base          │
│ VRAM 요구            │ ~76GB                     │ ~76GB (동일 아키텍처)              │
└──────────────────────┴──────────────────────────┴──────────────────────────────────┘
```

> **핵심 인사이트**: 두 모델은 동일한 Base 모델에서 파생되었으나, Thinking 모델은 **추론 능력**에, Coder 모델은 **코드 실행/수정 능력**에 최적화되었다. Non-thinking 모드는 응답 속도와 토큰 효율에서 큰 이점이 있다.

## 4. 듀얼 모델 밸런싱 전략

### 4.1 모델 할당 원칙

```
┌─────────────────────────────────────────────────────────────────────────────────────┐
│                           모델 할당 원칙                                              │
├─────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                      │
│  원칙 1: "추론이 핵심인 에이전트 → Thinking 모델"                                     │
│    - 복잡한 논리적 판단, 종합적 분석, 점수 산정이 필요한 작업                            │
│    - CoT(Chain-of-Thought) 추론이 품질에 직접 영향을 미치는 작업                        │
│                                                                                      │
│  원칙 2: "코드 생성/수정이 핵심인 에이전트 → Coder 모델"                                │
│    - SWE-Bench 스타일의 코드 수정, 버그 수정                                           │
│    - 코드를 읽고 직접 Edit하는 작업                                                     │
│    - Lint/Format/Build/Test 도구를 실행하는 작업                                       │
│                                                                                      │
│  원칙 3: "단순 도구 실행 에이전트 → Coder 모델 (속도 최적화)"                            │
│    - Non-thinking 모드의 빠른 응답 속도를 활용                                          │
│    - Thinking overhead가 불필요한 유틸리티 작업                                         │
│                                                                                      │
└─────────────────────────────────────────────────────────────────────────────────────┘
```

## 5. Context Window 공유 및 관리 전략

### 5.1 핵심 문제

```
┌─────────────────────────────────────────────────────────────────────────────────────┐
│                          Context 공유 문제 정의                                       │
├─────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                      │
│  LLM은 본질적으로 "프롬프트 입력 → 결과 출력" 의 Stateless 시스템이다.                   │
│  두 개의 모델을 사용할 때 다음 문제가 발생한다:                                          │
│                                                                                      │
│  1. 모델 A(Thinking)의 추론 결과를 모델 B(Coder)에 전달해야 함                          │
│  2. 모델 B의 코드 수정 결과를 다시 모델 A에 전달해야 함                                   │
│  3. 각 모델 호출은 독립적인 인퍼런스 세션 → 이전 대화 기록 없음                           │
│  4. 오케스트레이터가 모든 상태를 프롬프트에 포함시켜야 함                                  │
│  5. 프롬프트 크기가 커질수록 토큰 비용 + 지연시간 증가                                    │
│                                                                                      │
│  ┌─────────────────────────────────────────────────────────────────┐                 │
│  │  Model A (Thinking)          Model B (Coder)                    │                 │
│  │  ┌──────────────────┐       ┌──────────────────┐               │                 │
│  │  │ Prompt: 50K tok  │       │ Prompt: 80K tok  │               │                 │
```

### 5.3 Context Transfer 계층 구조

에이전트 간 전달되는 데이터를 3계층으로 분류하여 효율적으로 관리한다:

```
┌─────────────────────────────────────────────────────────────────────────────────────┐
│                       Context Transfer 3-Layer Model                                 │
├─────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                      │
│  Layer 1: Structured Tokens (항상 전달, 소형)                                         │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━       │
│  • ENV_STATE (셸, 환경, Python 경로, 활성화 명령)                                     │
│  • FILE_LIST (변경된 파일 경로 목록)                                                   │
│  • QUALITY_SCORE (품질 점수)                                                         │
│  • BUILD_RESULT / TEST_RESULT (SUCCESS/FAIL)                                        │
│  • COMMIT_RESULT (커밋 해시)                                                         │
│  → 크기: 약 1-3K 토큰                                                                │
│  → 모든 에이전트 호출 시 프롬프트에 포함                                                │
│                                                                                      │
│  Layer 2: Summarized Context (필요 시 전달, 중형)                                     │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━       │
│  • ISSUE_LIST (코드 리뷰 이슈 요약)                                                   │
│  • workspace_cache (프로젝트 구조 요약 JSON)                                          │
│  • 빌드/테스트 에러 로그 (핵심 부분만 추출)                                             │
│  → 크기: 약 3-10K 토큰                                                               │
│  → 관련 에이전트에만 선택적으로 전달                                                    │
│                                                                                      │
│  Layer 3: Raw Content (최소한으로 전달, 대형)                                          │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━       │
│  • 소스 코드 파일 내용 (에이전트가 Read 도구로 직접 읽음)                                │
│  • 전체 빌드 로그                                                                     │
│  • 전체 테스트 출력                                                                    │
│  → 크기: 10K-200K+ 토큰                                                              │
│  → 에이전트가 자체 도구로 필요 시 직접 획득 (프롬프트에 포함하지 않음)                     │
│                                                                                      │
└─────────────────────────────────────────────────────────────────────────────────────┘
```
